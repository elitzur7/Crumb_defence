# R3b — L38 smoothness at the new max speed

Gate: label 4x (6x the vc28 sim rate) on L38 for 40 s of 60 Hz frames (2400 frames). In-battle p95 frame work must be at most 22 ms. Desktop harness, headless Chrome, 393×852 @2x. Deck slingshot / spray / laser / zapper / fan, card level 4, autoplay on.

## Before

The harness called `battleFrame` and `renderOnce` in a tight loop and never returned to the browser.

| | ms |
|---|---|
| p50 | 1.4 |
| p90 | 2.8 |
| p95 | 210.7 |
| p99 | 225.3 |
| max | 281.5 |
| frames over 22 ms | 165 / 2400 |

**Result: fail.**

## What the stall was

The tail is one canvas flush, not a slow sim.

- Sim vs render, same scene: sim p95 was 0.2 ms. The ~250 ms sat entirely in render.
- It still happened with the bot off, with 0 ants and 0 particles.
- A full GC before every frame left the tail in place (p99 261 ms).
- Wrapping the canvas calls showed the stall landing on a different call each time (`fill`, `strokeText`, or a full-canvas `drawImage`). That is a sync point, not one expensive draw.
- `setTimeout(0)` between frames, so the browser can present, removed the tail (max 3 ms on a short run). A tight loop of plain `fillRect` did not stall, so the cost is a backlog of unpresented scene draws.

Chrome queues the canvas and, about every 40–50 frames, flushes the backlog onto whichever call is running. The game's own loop is one `requestAnimationFrame` per frame, which already yields. The harness now does the same: one yield per measured frame, and the page's rAF loop is stubbed so the battle is not stepped twice during that yield.

## After

Same scene, 2400 frames, yield once per frame.

| | ms |
|---|---|
| p50 | 1.9 |
| p90 | 2.9 |
| p95 | 3.5 |
| p99 | 7.8 |
| max | 20.4 |
| frames over 22 ms | 0 / 2400 |

**Result: pass.** p95 3.5 ms is under the 22 ms line. Measured on the build that also has the softer play ants and G14 variety.

Raw after-run: `qa/v0.8.4/r3b-raw.json`.
